# 结构化槽位信息

完整字段、四态及关联校验见本包 [槽位快照规范](requirements-schema.md)，槽位名称和范围见本包 [槽位分类](slot-policy.md)。

requirements_input 是调用方提供的完整槽位快照，结构为：{ "槽位分析": {槽位名称: 定位记录数组} }，正式对象保留本版全部28个槽位键。它是共同需求底稿，不再另生成按业务主题分类的需求摘要。本 skill 仅依据输入快照生成方案，修改时只增量更新本次涉及记录，不重跑全量需求分析。

## 简短示例（节选）

```json
{"槽位分析":{"审批人类型":[{"id":"s06","定位":"资产领用申请/审核节点","已知信息":"部门主管","状态":"resolved","依据":[{"来源":"q1回答","原文":"部门主管审批","推导理由":null}],"缺口或冲突":null,"是否需澄清":false}]}}
```

每条记录固定包含 id、定位、已知信息、状态、依据、缺口或冲突、是否需澄清。id 为记录的稳定非空字符串，在整个需求对象内唯一；四态及分类按本包 requirements-schema.md 与 slot-policy.md 判断。修改内容、改名或调整定位时沿用 ID；新增记录分配未使用 ID；删除时不能复用旧 ID。不能以变更后的文字或数组下标当作身份。

输入须含完整快照，不接收或重读问答历史。missing/partial/conflict 不被完整方案抹平；本 skill 按调用契约判断是否可识别业务意图，不另在快照中增加可生成标记。

本 skill 返回更新后的 requirements_input，后端将它作为同一需求底稿的新版本，与方案正文、搭建计划一同保存。不存在两份独立维护的需求。只允许更新用户明确变更及必要依赖，原明确需求持续生效；AI设计补全按下文独立标记来源，不能冒充用户已确认的业务事实。

## 关联与边界

应用搭建计划通过 requirement_ids 引用本对象中的记录 id，一个项目可以关联多条记录。不另建映射表，不给方案段落建立槽位映射；用户页面、方案正文和下载文件均不展示内部 ID。后台接口及研发示例可以包含 ID。

C 类已提出的要求及冲突仍保留在对应槽位，默认不追问，不能因当前不可自动实现而删除。仅属完整建设方案的人工扩展功能不强行加入本次搭建清单。

## 不匹配与迁移

新增业务需求能归入现有28槽位但无旧记录时，按原定义新增记录并分配新 ID；目标或含义不明则针对本次修改提问，保留原版本；仅表达或排版变化不新增记录；确实超出槽位定义时保留原请求并说明分类待确定，不臆造槽位；已明确的扩展业务目标按定义保留在相应业务环节中，不把不明内容随意归入。

旧版主题汇总输入或无 ID 快照应由调用端先迁移到本结构，校验后再继续修改。不能直接用旧摘要重新初始化并改变已确认事实，也不能用空对象冒充完整快照。

## 设计补全的记录来源

需求解析不凭空补造用户需求。为本次计划补出的低风险具体设计，如常规字段类型、图表维度与聚合选择，应写入相应槽位并分配稳定ID，依据明确标记 {来源:"AI设计补全",原文:null,推导理由:"基于哪些已有业务需求作出的设计"}。它是设计候选，不是用户原话；用户确认最新计划后才可据此执行。resolved 在此只表示设计已具体，不等于用户已确认。不得用此机制擅定审批人、阈值、关键权限或新增业务范围；关键未知仍保留待确认。
