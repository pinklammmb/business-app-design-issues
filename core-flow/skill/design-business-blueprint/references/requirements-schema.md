# 结构化槽位快照规范

完整快照固定为 {"槽位分析":{槽位名称:记录数组}}，保留 [槽位分类与范围](slot-policy.md) 列出的全部28个名称，不增删槽位键。每项值为数组；暂未适用时为空数组，不把未提及解释成不需要。requirements_input 和响应内的 state.requirements 使用此结构；具体操作是否读写由本包调用契约规定。

## 定位记录

每条记录固定包含以下字段：

| 字段 | 类型与要求 |
| --- | --- |
| id | 非空字符串，整个快照内唯一；改名、修正沿用，新增分配新ID，删除不复用 |
| 定位 | 非空字符串，指明业务、对象及必要的字段或节点；同名对象分别定位 |
| 已知信息 | 字符串或null；missing为null；conflict保留互斥候选，不替用户选择 |
| 状态 | resolved / partial / missing / conflict |
| 依据 | 数组，每项固定为来源、原文、推导理由 |
| 缺口或冲突 | 字符串或null；resolved为null，其余写实际缺口或矛盾 |
| 是否需澄清 | 布尔值，按类别与四态计算，不等于发布许可 |

依据.来源为非空字符串；原文、推导理由为字符串或null。直接提取必须有真实原文；有据推导须有理由。missing无依据时为空数组；conflict分别保留候选依据。低风险设计补全的来源固定为“AI设计补全”、原文=null、推导理由非空，不冒充用户事实或已确认。不得擅定审批人、阈值、关键权限或业务范围。

## 判态与澄清标记

- resolved：用户已明确或有依据可推导，信息足够具体；不等于用户已确认，也不等于已搭建。
- partial：已提及，但缺少会实质影响业务的关键决定。
- missing：未提供且无法推导；平台不支持某要求不等于missing。
- conflict：排除明确修正与兼容补充后，同条件要求仍不能同时成立。

每条定位记录独立判态，不输出槽位总状态。明确修正替换、兼容补充合并，其余要求与依据保留；不按消息时间自动覆盖。角色与业务规则的含义明确不要求真实人员账号，运行时真实组织映射另行核验。

| 类别 | resolved | partial | missing | conflict |
| --- | --- | --- | --- | --- |
| A | false | true | true | true |
| B | false | true | false | true |
| C | false | false | false | false |

标记描述需求是否需要澄清，当前操作是否允许发题由本包契约规定。配置生成不得因此自行追问或修改已确认快照；只能报告相关缺口和执行限制。C类保留原要求、候选与影响，关键权限或校验未知仍可限制发布。

## 关联与交付

application_build_plan中的requirement_ids只能引用同版快照内存在的记录ID；不以名称、数组下标或平台应用ID替代。AI补充的执行必需设计先写回快照再关联。计划应用及子项ID与槽位记录ID分别管理，不另建正文段落映射。

快照、计划和方案由调用方同版保存；不能只凭一个路径、历史节点名称或聊天摘要恢复输入。内部ID只用于后台关联，不进入用户方案正文、页面和下载内容。只读操作保留快照；可修改操作只更新本次相关记录及必要依赖。
