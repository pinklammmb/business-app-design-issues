# 回答的增量更新

## 关联与范围

回答通过 question_id 对应当前批次，结合问题关联的槽位、定位及答案解释语义。“其他”和输入框是对本题的回答，不是自由需求入口。

- 本题范围内的补充信息可更新多个相关槽位，例如回答“需要，由管理员审批”同时明确审批类型和审批人。
- 本题范围内的明确修正可替换旧要求，例如“不再需要部门主管，只保留管理员”；不能因修正就新建冲突。
- 明显无关的新增业务，例如回答审批问题时要求“另外增加维修系统”，不合并需求、不新增问题，将原文放入 deferred_content，说明可在业务系统建设方案修改阶段处理；同时正常处理同一回答内有效的本题答案。
- 不因不清楚回答对应哪题而猜测；question_id 错误按调用错误返回，不消费轮次。

## 更新步骤

1. 将回答作为来源依据合并到关联记录；保留已知内容、具体缺口和候选值依据。
2. 先识别明确修正，再合并兼容信息，最后判断无法兼容的真实冲突；再检查信息是否足够。相关字段已有完整答案时置 resolved，无法确定的部分保留原状态或按实际改为 partial / conflict。
3. 仅更新直接涉及和依赖受影响的记录，未受影响记录按原值保留；不重新读取附件或扫描全量槽位找新缺口。
4. 依赖不再适用时清除其有效槽位记录，并把清单项置 obsolete；原要求及问答可在清单与问题历史中追溯，不保留失效旧值冒充当前需求。
5. 更新清单进度：解决即 resolved；部分回答缩小缺口；明确跳过为 skipped；该批提交后遗漏或“不知道”类无有效答案为 unanswered。后两者不等于需求明确或接受默认值。
6. 本题回答所导致的冲突或必要依赖缺口可入清单；必须记载触发依据并按矩阵确定是否需澄清。
7. 本批处理后，无可问事项或第三轮已完成则结束，否则生成下一批；单题跳过不直接结束整个流程。输出完整新状态；update_log 仅列实际变更，供研发检查和追踪。完整快照中的未变记录不重写语义。结束时另按 blueprint-input.md 汇总完整有效需求为 requirements_input，不把增量日志当作最终需求。

用户提交的是整批回答。未提交草稿不属于有效依据。调用方可允许部分提交，但提交时遗漏的题不默认为“否”。
增量更新沿用原记录 id；新增记录分配新 id；删除不复用旧 id。结束时 requirements_input 与 state.requirements 完全一致，后端校验后保存同一份需求底稿。
