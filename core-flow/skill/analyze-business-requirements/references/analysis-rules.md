# 首轮提取与记录规则

四态和矩阵以 state-rules.md 为唯一判定定义；本文件补充 initialize 的提取顺序与去重。

## 判断顺序

1. 提取有效原文，按槽位和业务定位归集。定位可为系统整体、业务、业务对象、字段或节点；归属尚不清楚时写“待确定”，不要求先有应用。
2. 结合完整上下文推断，保留依据和推导理由，不把默认做法作为事实。
3. 先识别明确修正，再判断是否兼容或可合并，最后才判定冲突。明确取消、替换或限定保留范围时更新有效要求；新增信息与旧要求可同时成立时合并。仅在同一业务、同一定位和条件下的有效要求无法同时成立，且无法确定替换关系时记为 conflict。不能仅因增加了信息就判冲突，也不能仅因出现更晚就覆盖旧要求。排除修正和兼容补充后，再判断信息是否足够；有实质缺口为 partial，无信息为 missing，足够确定为 resolved。
4. 不同业务或条件下的不同值不直接算冲突。收到修正或补充后重新判断受影响记录，撤销失效的旧冲突；要求已明确时记 resolved，有其他缺口则按实际判态。

仅当缺口同时满足“无法合理推断”“必须由用户决定”“不同答案实质影响范围、流程、数据含义或权限”时，才归入 partial。缺少控件、长度、颜色、布局等常规配置，不降低已明确业务意图的状态，也不额外创建待澄清记录。不能借此自行填写审批阈值或权限边界。

## 依赖与去重

- 未提及不等于不需要；明确“不需要”可为 resolved。
- 先判定是否需要审批。未确定或明确无需审批时，不展开该业务的节点名称、节点类型、节点顺序、审批人类型、抄送、分支、两类节点高级设置和角色权限中的节点字段约束，除非用户已直接提供这些信息。
- 按定位判断依赖，一项业务无需审批不影响另一项业务。
- 同一具体信息归入一个槽位；同一段原文包含多种独立事实时可以分别提取，不重复制造缺口。
- 应用清单允许推导必要业务对象，但不提前固定物理拆分或虚构类型。

按 state-rules.md 的类别矩阵计算是否需澄清，不因不追问而将未知改为 resolved。解析阶段只标记，随后由清单规则生成问题。
