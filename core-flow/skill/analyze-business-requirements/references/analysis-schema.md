# 输出规范

本文件定义 initialize 内部解析快照 requirements，顶层仅包含“槽位分析”。快照放入最终响应的 state.requirements；不单独返回，外层响应以 output-schema.md 为准。

完整通用字段及判态定义见本包 [槽位快照规范](requirements-schema.md)；下文补充解析操作的记录生成要求。

## 槽位分析

对象包含槽位定义中的全部 28 个槽位名称，每个名称的值为定位记录数组。类别按本版槽位名称及范围确定，不重复输出类别或槽位总状态。已支持与未支持范围使用不同的槽位键，不能混写。

单条记录固定为：

```json
{
  "id": "s01",
  "定位": "资产使用申请",
  "已知信息": "普通用户可以提交资产使用申请",
  "状态": "partial",
  "依据": [
    {"来源":"用户输入","原文":"普通用户可以申请使用资产","推导理由":null}
  ],
  "缺口或冲突": "是否需要审批通过才能使用资产",
  "是否需澄清": true
}
```

- id：非空稳定记录 ID，整个需求对象内唯一；新增时分配，修改或改名沿用，删除不复用。
- 定位：非空字符串，同一槽位可有多条不同定位记录。
- 已知信息：字符串或 null；部分信息保留原意，missing 为 null；conflict 在字符串中分别列出候选值，不选择其中之一。
- 状态：resolved / partial / missing / conflict。
- 依据：数组，各项固定为“来源”“原文”“推导理由”。快照可保留来源为“AI设计补全”、原文为null且推导理由非空的合法设计记录；本 skill 不据此虚构用户输入。来源用用户消息标识或“附件文本1”等输入位置标识，不要求附件文件名或页码；直接提取的推导理由为 null，推导所得填写理由。无原文可引用的 missing 记录依据为空数组，不编造引文；冲突记录须分别保留各候选值依据。
- 缺口或冲突：字符串或 null；resolved 为 null，其余写明实际缺口或矛盾，不写问题句。
- 是否需澄清：JSON 布尔值，按类别矩阵计算。

## 记录生成规则

- 已知要求及适用业务中的必要缺口生成记录，不为未知业务、字段或节点预建占位记录。
- 本次全部有效文本中整项槽位未提及且无依赖障碍时，输出一条“系统整体”的 missing 记录；A 类据此标记澄清，B/C 类不问。不要把未提出的扩展能力逐项列为缺失，也不要因技术实现未定而把已明确的业务目标改成缺失。
- 暂未激活或不适用的槽位，数组为空。已有部分适用业务时，仅输出该部分有效记录，不补全假想对象。
- 28 个槽位键均保留；空列表表示尚不分析该项，不表示用户明确不需要。结合业务依赖记录解释。

## 输出前校验

1. JSON 可解析，字段和枚举符合规范，28 个槽位键齐全。
2. 已知信息有原文依据，推导有理由；只依据本次全部有效文本判断业务缺口。
3. 同一槽位的不同定位独立判态，没有重复事实或假冲突。冲突候选须为仍有效、无法同时成立的要求；明确修正已替换的旧值不列为冲突候选，可兼容补充应合并，不能只因审批人增加就标记 conflict。
4. 常规设计细节没有被标成待补全；审批依赖项没有提前展开。
5. 澄清标记符合矩阵；解析子步骤不生成问题、业务系统建设方案或搭建配置，随后在同次 initialize 中按清单规则生成首批问题。
