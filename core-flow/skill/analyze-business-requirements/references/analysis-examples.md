# 判定示例

以下为局部记录的判断示例，不是最终完整输出；正式结果保留全部槽位键并遵循输出规范。

## 简短资产需求

输入：“搭建一个学校资产管理系统，普通用户可以申请使用资产，管理员负责管理资产出入库。”

- 名称、业务环节、角色及明确职责可 resolved，不额外添加学生、教师或校长。
- 应用清单可推导资产台账、申请及出入库记录等必要业务对象，不将其认定为必须独立创建的四个应用。
- 资产使用申请是否必须审批不能由“申请”确定，审批类型判定为 partial，标记需澄清。
- 出入库只明确管理员操作，审批要求未提供且无法推断，可记录 missing，按本版 B 类暂不主动追问；不自动指定管理员审批。
- 审批尚未确定，节点名称、节点类型、节点顺序、审批人类型、抄送、分支、两类节点高级设置及节点内字段权限不提前展开，不用“待确定”批量创建 missing 占位记录。
- 不添加归还、维修、报废、扣库存触发时点或仪表盘等无依据需求。

## 可推断与常规设计

输入：“员工提交后由主管批准，记录姓名和申请数量，需要按月看申请数量。”

- 审批类型及审批人可 resolved，姓名为文本、申请数量为数字可依据含义推导。
- 仪表盘主题已明确，不因缺少图表类型和布局而记 partial。
- 不要求用户指定字段长度、菜单树或真实主管账号。

## 真正缺口

输入：“按金额分级审批。”

审批分支条件已提及，但阈值和对应审批路径无法确定，记 partial，审批分支条件属于 C 类，默认不追问；保留到业务系统建设方案并披露相关流程本次不能自动配置，不得采用行业常见金额阈值补齐。

## 修正、兼容补充与冲突

- 明确修正：“不要部门主管审批节点了，只保留管理员审批节点。”替换原规则，仅保留管理员节点；在其余要求足够确定时为 resolved，不追问已经取消的节点，也不保留失效冲突。
- 明确补充：“除了管理员，还需要部门主管审批。”合并两者，不记 conflict；不自行决定审批顺序，只按实际缺口和澄清规则处理。
- 可兼容表述：“请假需要管理员审批。请假需要管理员和部门主管审批。”前一句未限定“只需要管理员”，可合并为两者均参与，不因参与者增加就判冲突；顺序若有实质缺口另行判断。
- 真正冲突：“请假只需要管理员审批，不经过部门主管。请假必须经过管理员和部门主管审批。”同一适用条件下无法同时成立，又无明确修正关系，相关节点要求记 conflict，保留双方依据并标记需澄清。

仅因后文更晚不能覆盖互斥要求；明确“改为”“取消”“只保留”等修改意图可替换旧要求，不要求用户必须使用固定词语。

## 其他能力

输入：“审批通过自动扣减库存，每月生成资产盘点报告。”

在对应业务环节中分别保留自动更新库存与报告输出的扩展目标和原文；不因出现“扣库存”就额外要求聚合表，也不直接认定报告必须由某个引擎实现。

## 文档附件文本

输入 user_input：“按附件要求搭建”；materials：[“学校资产管理系统，管理员登记资产，普通用户查看资产，无需审批。”]。

将两部分文本一并分析，提取名称、角色、业务对象和无需审批的要求；不请求原附件文件，也不输出附件来源、完整性或读取问题。依据可标“附件文本1”并引用原文。

## C 类不因冲突而追问

“资产分类只有固定资产、耗材”与“资产分类只有设备、家具”，同条件下无法判断修正关系：字段选项值记 conflict，保留双方依据，是否需澄清=false。不替用户选择选项，不承诺自动写入；业务系统建设方案注明待人工确认并补配。

“字段清单”现为 B 类；例如用户明确提出必须记录某项业务信息但含义存在实质歧义，可按 partial 澄清。未提供所有常规字段时不逐项出题。
