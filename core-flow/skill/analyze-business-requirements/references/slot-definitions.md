# 槽位定义

共28个槽位，按本版清单固定名称和分类；每个槽位含定位记录数组，不为同一槽位输出总状态。四态与追问规则见 [状态规则](state-rules.md)。

| 类别 | 槽位 | 范围 |
| --- | --- | --- |
| A | 业务系统名称 | 业务系统建设方案基本信息，无需这三个 skill 执行 |
| A | 业务环节 | 业务范围描述 |
| A | 主要使用角色 | 使用对象描述；实际角色授权另归 C 类 |
| A | 应用清单 | 业务系统建设方案中的对象规划；清单内各应用的创建分别判断 |
| B | 应用名称 | 表单、审批、仪表盘的名称；与 A 类业务系统名称区分 |
| B | 审批类型判定 | 判断采用普通表单还是审批表单，并选择对应创建 skill |
| B | 字段清单 | 可创建字段名称及对应组件；子表单等容器类字段除外 |
| B | 字段名称 | 字段的显示名称 |
| B | 字段类型 | 支持白名单内且当前协议可传入的类型 |
| B | 字段顺序 | 按字段配置数组顺序生成，实际展示效果待平台验证 |
| B | 节点名称 | 审批、抄送节点的名称 |
| B | 节点类型 | 审批 / 抄送 |
| B | 节点顺序 | 支持顺序审批、抄送，不含条件分支 |
| B | 审批人类型 | 明确支持主管、角色；其他类型待确认 |
| B | 抄送需求 | 支持指定成员、主管、角色抄送 |
| B | 节点高级设置：协议已有参数 | 支持协议已列明的审批方式、主管层级、找不到主管时的处理等参数，具体取值遵循协议 |
| B | 仪表盘需求 | 支持真实数据源下的规定组件与统计配置，最多 8 个组件；接入状态待验证 |
| B | 仪表盘组件类型 | 限 13 类组件白名单，每份配置最多 8 个组件 |
| B | 维度字段 | 绑定真实字段，遵守非数值维度及各组件维值组合限制 |
| B | 指标字段 | 绑定已有真实字段，不自行推导计算指标 |
| B | 指标聚合方式 | 数值支持总数、平均值、最大值、最小值、次数；文本与日期仅支持次数，并遵循字段提供的聚合能力 |
| C | 菜单导航设计 | 分组、菜单层级、前后台入口及实际配置；可在建设方案描述，当前创建skill不自动配置。 |
| C | 角色权限 | 菜单、数据、字段及功能权限，包含审批节点内的字段可见、只读和可编辑权限。 |
| C | 应用绑定组织架构 | 应用或应用包与部门、成员、角色的组织范围绑定；不自动配置。审批节点引用已有主管、角色仍按B类审批人类型及节点参数处理，真实映射由后端核验。 |
| C | 审批分支条件 | 不支持条件分支与路由配置 |
| C | 字段选项值 | 当前搭建协议未定义单选、下拉框、多选下拉的选项传输，需人工补配 |
| C | 字段属性设置 | 必填、默认值、日期精度、公式、校验及关联规则等无法通过当前协议完成；名称、类型已单列为 B 类，选项值另列为 C 类 |
| C | 节点高级设置：协议外参数 | 超出协议已列明参数的设置无法实现 |

## 提取与记录边界

- 同一事实只归一个槽位。应用清单表达业务对象与用途，应用名称表达具体名称；字段清单表达记录哪些信息，字段名称、类型和顺序分别记录具体要求。
- 对象、字段、节点与组件按业务定位分别记录；同名字段不跨应用合并。每条记录ID稳定，计划以requirement_ids关联记录。
- 应用绑定组织架构属于C类，审批人类型及协议内节点参数属于B类：应用组织范围绑定与节点引用已有主管/角色不得混为一谈；真实角色、部门、成员由后端核验。
- 角色权限包含节点内字段权限；菜单导航设计包含结构与实际配置，均为C类默认不问。
- 业务系统名称可依据明确业务主题归纳，不为措辞单独追问；应用清单可从已明确业务推导必要承载对象，不增加无依据的维修、报废或看板业务。
- “申请”不必然等于需要审批；是否需要审批未确定时，不展开节点和办理人缺口。审批、抄送、分支及节点设置分开归类。
- 图表组件、维度、指标及聚合按已有业务含义记录；实际sourceId、fieldId在搭建时获取，不要求用户填写技术ID。
- 低风险常规设计可以补齐并标记AI来源；审批人、阈值和关键授权不能擅定。

## 扩展需求的保留

不再设置独立的其他能力槽位。用户已提出的提醒、业务联动、报表、集成等要求，按业务目的在相应业务环节记录中保留原文和约束；不为其技术实现细节额外追问，不扩入本次搭建承诺。真正的业务目标缺口仍按A类规则处理。

## 业务语义参考


### 业务系统名称

- 含义：系统或应用包的整体名称，供业务系统建设方案第 1 章使用。
- 定位：系统整体。
- 已明确标准：用户明确命名，或可以从明确业务主题归纳名称。例如“管理学校资产”可推导为“学校资产管理系统”。
- 边界：不包含应用名称、导航分组名称；无须为命名措辞追问。

### 业务环节

- 含义：系统要解决的问题、覆盖的业务活动及其关系，包括明确的本期范围和排除项，供业务系统建设方案第 1、2 章使用。
- 定位：系统整体或具体业务。
- 已明确标准：能说明做什么、哪些活动在本次范围内。例如申请使用资产、资产入库、资产出库。
- 边界：不要求完整审批节点或实现方案；不因常见资产系统具有归还、维修、报废，就自动加入这些环节。明确不做的事项作为范围约束保留。

### 主要使用角色

- 含义：使用系统的业务身份及其职责，供业务系统建设方案第 1、6 章使用。
- 定位：系统整体，或用户描述了局部身份差异的业务。
- 已明确标准：能识别参与者及其主要职责。例如普通用户申请使用资产、管理员管理出入库。
- 边界：不要求真实人员名单或组织绑定；不能仅因场景是学校，就自行添加教师、学生、校长等角色。

### 应用清单

- 含义：承载已知业务所需的业务对象及用途，是业务系统建设方案第 2 章对象清单的需求依据。
- 定位：系统整体或具体业务，每条记录可包含多个相关对象。
- 已明确标准：用户直接列出对象，或可从业务活动推导出必要对象及用途。例如资产台账、资产使用申请、入库记录、出库记录。
- 边界：不要求用户指定对象的物理拆分、最终命名或菜单入口；不能将业务环节机械等同于独立应用。审批类型由专门槽位判断，不因应用类型暂未确定就否定已知对象；不新增无依据的仪表盘和可选能力。

### 审批类型判定

- 含义：某项业务是否必须通过审批才能继续，决定是否按审批业务设计，供业务系统建设方案第 4 章使用。
- 定位：具体业务或申请事项。
- 已明确标准：用户明确需要或无需审批，或描述了明确的审核通过条件，例如“主管批准后才可领用”。
- 边界：“申请”不必然等于需要审批；“管理员负责管理”不代表管理员是审批人，也不代表无需审批。未提及审批不能直接确定为不审批。节点、审批人、分支分别归入专门槽位。

### 字段类型

- 含义：字段承载的数据含义、精度和输入形式要求，对应业务系统建设方案第 3 章。
- 定位：具体字段。
- 已明确标准：类型已指定，或可依据含义推导。例如姓名为文本、数量为数字；无需逐项追问控件。
- 边界：日期精度等仅在不同解释实质影响业务时形成缺口。用户描述优先按原义保留，平台不支持的类型不能改写成其他类型或视为用户缺失。
- 后续设计约束：生成规则列出的类型为单行文本、多行文本、数字、日期、日期时间、下拉框、单选、多选、联系人、部门、附件、图片、子表单。此白名单用于后续设计适配，不要求用户从中逐一选型。

### 字段清单

- 含义：需要记录哪些业务信息，以及字段的业务含义和明确关联，对应业务系统建设方案第 3 章。
- 定位：业务或业务对象。
- 已明确标准：已提出的字段要求足够确定，例如“记录资产名称、编号、存放地点”；无需完整枚举最终建表字段。
- 边界：类型归“字段类型”，选项归“字段选项值”，必填等属性归“字段属性设置”。未提到的常规字段留待后续设计，不提前声称用户已要求。

### 仪表盘需求

- 含义：需要查看的统计结果、指标、分析维度及业务口径，对应业务系统建设方案第 5 章。
- 定位：具体统计主题或看板。
- 已明确标准：能确定要看什么数据或回答什么问题。例如“按资产类别统计库存数量”。
- 边界：不要求指定图表类型、配色和布局。若“使用率”等指标存在多种会影响结果的业务含义且无法推断，才记录口径缺口。跨表数据处理的扩展目标归相应“业务环节”说明，可视化诉求归本槽位，不重复提取同一信息。

### 审批人类型

- 含义：每个审批节点由谁办理，以及如何确定该办理人，对应业务系统建设方案第 4 章。
- 定位：审批业务下的节点；尚无节点名称时用已知业务描述定位。
- 已明确标准：办理身份或选取规则可确定，例如固定管理员、发起人所在部门负责人；明确要求的多人处理规则归节点高级设置。
- 边界：不要求真实姓名或账号才能认定业务规则明确；“管理员管理资产”不能直接推断为“管理员审批申请”。

### 抄送需求

- 含义：在业务办理的指定时点，将相关信息抄送给谁，是流程设计的补充信息。
- 定位：审批业务或具体节点。
- 已明确标准：用户要求的抄送对象与时点足够确定。
- 边界：抄送不等于审批，不产生同意或拒绝权。独立的定时提醒、库存预警等扩展目标归相应“业务环节”说明；未提及不主动添加抄送。

### 审批分支条件

- 含义：依据何种条件进入不同节点或路径，对应业务系统建设方案第 4 章分支规则。
- 定位：审批业务及具体分支。
- 已明确标准：条件及其对应去向可确定，例如“金额超过一万元由校长审批，其余由部门负责人审批”。
- 边界：不能自行补金额阈值、判定条件或关键去向。仅说“按金额分级审批”且无法推导阈值时属于实质缺口。没有分支诉求时不主动设计并追问分支。

### 字段选项值

- 含义：枚举类字段允许选择的业务值及明确的选值限制，对应业务系统建设方案第 3 章。
- 定位：业务或对象下的具体字段。
- 已明确标准：已说明用户要求的选项，或能从已知业务状态推导；明确提出自定义分类但未提供分类内容时保留具体缺口。
- 边界：不要求用户列全所有未来字段的选项，不自动创建未提及的分类体系。字段类型归“字段类型”，默认选项归“字段属性设置”。业务系统建设方案最终枚举写全的要求不转化为首轮全量追问。

### 字段属性设置

- 含义：必填、默认值、唯一性、校验、计算公式和明确的关联约束，对应业务系统建设方案第 3 章的必填、默认值、公式及说明。
- 定位：具体字段。
- 已明确标准：已提出的约束有可理解的业务含义；常规属性无需逐项确认。
- 边界：不包含字段类型、枚举值和权限。单字段公式归本槽位，跨表汇总、跨表写入或专门数据处理的扩展目标归相应“业务环节”说明。

### 角色权限中的节点字段约束

- 含义：特定审批节点内，办理人能看到或修改哪些字段，对应业务系统建设方案第 4 章字段权限。
- 定位：审批节点及相关字段。
- 已明确标准：用户提出的节点内权限要求可确定，例如“申请人填数量，管理员只填写实际出库数量”。
- 边界：模板中的“全部字段”是占位示例，不是默认用户授权。与一般角色在应用中的权限统一归入“角色权限”，同一约束不重复记录。

### 业务环节中的扩展目标

- 含义：基础表单、审批、仪表盘、导航及权限之外，用户明确提出的业务能力。主要对应业务系统建设方案第 7 章，保留到对应业务环节记录，不作为所有未归类信息的杂项桶。
- 定位：具体能力及其相关业务；在相应业务环节保留扩展目的与约束。

| 能力 | 识别的业务要求 | 与其他槽位的边界 |
| --- | --- | --- |
| 聚合与提交限制 | 根据已有数据按条件汇总，并限制本次提交，例如累计领用量不能超过库存 | 不等同于仅展示库存统计；记录计算口径及上限要求，不强迫用户选择“聚合表”技术方案 |
| 业务流 | 在新增、修改、审批通过或定时等条件下，自动向其他对象写入或更新数据，例如审批通过后扣减库存 | 不等同于审批节点流转；保留触发、目标和变更效果，不能推断出入库的具体触发时点 |
| 数据工厂 | 专门的数据取数、过滤、分组计算、结果输出及存储要求 | 不因需要一张统计图就自动加入数据工厂；可视化主题归仪表盘需求 |
| 报告引擎 / 报表引擎 | 基于指定数据生成报告或报表的业务用途及内容要求 | 不将用户口语中的“报表”直接认定为报表引擎；依据其实际需要区分统计看板与报告输出，保留尚不明确的描述 |
| 推送提醒 | 在事件、日期或定时条件下，向相关人员提醒的要求 | 模板生成规则及实施步骤提到提醒，但未定义渠道能力；不能自行断言短信等渠道可用；流程抄送归抄送需求 |
| 其他明确能力 | 用户明确提出的外部集成、导入导出或其他未被现有槽位覆盖的能力 | 这些能力是补充识别范围，不代表模板承诺支持；若仅描述谁可以导入导出，归角色权限 |

- 已明确标准：用户提出的业务目的和要求足够理解；不要求首轮补齐技术配置。业务目标本身按 A 类判断；不为扩展的技术实现细节追问，未实现范围保留候选与影响。
- 排除：已归属专门槽位的信息、系统总体范围、常规设计细节、实施顺序和交付状态。未提及的能力不主动添加或逐项列为缺失。
- 能力可实现性：平台是否支持与用户需求是否明确是两件事。本环节保留需求，不承诺支持，也不因不支持而改为用户信息缺失。

## 旧快照迁移

- 原菜单导航的结构描述与实际配置记录归入“菜单导航设计”。
- 原组织架构绑定的引用与创建维护记录，按应用绑定语义归入“应用绑定组织架构”；其中实际描述节点办理规则的记录按其含义归入“审批人类型”或“节点高级设置：协议已有参数”。
- 原节点字段权限记录归入“角色权限”；原其他能力记录按业务目的保留到“业务环节”的扩展说明。
- 迁移只是重新归类，保留每条原记录ID、原文、定位及有效约束，不能合并不同ID后让计划引用失效；重新计算类别和澄清标记。无法唯一归属的记录先核实，不按新表静默丢弃。确认前完成快照和计划引用校验，历史执行版本保留不改。
