# 表单与审批的创建页流程

本文件是本流程的最新产品口径，优先于旧接入材料中先创建空白应用、再传配置的描述。适用于表单和审批；仪表盘仍按 dashboard-adapter.md 的独立约定处理。

## 正常路径

1. 用户确认应用搭建计划，后端按任务顺序打开对应的空白创建页。此时仅打开页面，不代表已有真实应用，也不要求预先拿到应用ID。
2. generate_config 返回应用配置 JSON 对象；后端校验并保存为该任务的 JSON 文件。JSON文件的内容就是 config，不包含 ref、requirement_ids 或外层状态字段。
3. 创建页读取该应用配置 JSON 文件，在页内回显应用名称、字段及审批节点。无需用户重复录入，也不描述成对已存在应用“覆盖配置”。
4. 创建页根据回显内容完成创建，随后在发布许可允许时自动发布。
5. 发布成功后回传真实应用ID，后端校验可信来源及当前任务绑定，再记录 published 和 published_id；创建页已打开、JSON已生成或页内已回显都不能记为发布成功。

已有关键缺项时仍执行 capability-policy.md 的发布限制，不能为了自动发布而绕过权限、审批或关键校验。回显可以用于核对与补齐，但不等于已创建应用成果。

## 状态与配置输入

表单/审批的配置生成前置状态为 page_ready，由前端实际空白创建页加载结果记录；此时 blank_app_id 可以为 null，不伪造页面就绪回调或应用ID。尚未打开或未就绪时 waiting。config_ready 表示JSON对象已生成，configured 对表单/审批仅表示文件已读取并在页内回显，不保证已创建、保存或发布。只有实际成功回传后才写 published_id。

创建页文件交付、读取入口、读取完成或失败通知、创建失败和发布失败的查询对账，仍需研发按实际实现补齐；本包不编造文件URL参数、上传接口或跨源消息。旧 session-storage-contract.md 仅复用已定义的配置内容结构和发布成功消息作为现有参考，不能直接声称 sessionStorage 就是JSON文件读取接口；旧的写入存储再跳转步骤不作为当前产品主流程。

原已知成功消息形状为 {action:"published",from:"form"或"aprv",data:{formId:真实ID}}，具体是否沿用以创建页实际回传契约为准；没有实际回传证据时不得伪造。后端把实际 formId 映射为内部 published_id，逻辑任务ref与平台应用ID分开。
